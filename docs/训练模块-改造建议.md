# 训练模块 · 改造建议（科学版）

> 基于现有 `training.html` / `training-big3.html` / `training-plan.html` 的实际数据与代码。
> 目标：训练记录从「打卡」升级为「可判断进步、可指导下一次」的系统，同时保持 30 秒单手记录。

---

## 一、现状的 5 个硬伤

1. **时长是假的**
   `markDone()` 每完成一个动作就写 `LightStore 运动 10 分钟`（热身 5 分钟），与实际训练时长无关。
   力量记录的 `minutes` 甚至是 0。结果：体账户分数、灯的判定被虚构数据影响。

2. **没有「一次训练」这个实体**
   记录是「一个动作一条」（`lifeflow-train-records`），同一天的动作没有 session 归组；
   无法回答「今天练了多久、总量多少、强度如何」。

3. **没有强度指标**
   有重量/次数，但没有 RPE/RIR、组间休息、动作难度；
   无法判断「80kg×5」是轻松还是力竭，也就无法科学加量。

4. **计划是写死的**
   「练 3 休 1」「三大项每周一/五」写死在页面里；没有按恢复、按目标调整。

5. **三个页面各自实现**
   `training` / `big3` / `plan` 各自维护 plan/records 常量与读取逻辑，容易漂移。

---

## 二、目标模型：一次训练 = 一个 Session

建议新增 `lifeflow-train-sessions-v2`（旧 records 只读迁移）：

```json
{
  "v": 2,
  "sessions": [{
    "id": "s_20261021_1",
    "date": "2026-10-21",
    "kind": "strength",
    "start": "19:10",
    "end": "20:05",
    "durationMin": 55,
    "sessionRpe": 8,
    "exercises": [{
      "name": "深蹲",
      "muscle": "legs",
      "sets": [
        { "weight": 80, "reps": 5, "rpe": 8, "restSec": 150 },
        { "weight": 80, "reps": 5, "rpe": 9, "restSec": 180 }
      ]
    }],
    "cardio": null,
    "notes": ""
  }]
}
```

派生指标（不落库，实时算）：

- **容量** volume = Σ(weight × reps)（自重按体重比例或记 reps）
- **e1RM** = weight × (1 + reps/30)（Epley，仅作趋势）
- **有效组**：RPE ≥ 7 且 5 ≤ reps ≤ 30
- **每肌群周组数**、**每周频率**、**4 周依从率**
- **急性/慢性负荷比**：近 7 天容量 ÷ 近 28 天周均（0.8–1.3 安全区）

## 三、三层改造

### P0 · 先把数据修对（2–3 天）

1. 新增 `pages/core/training.js`（纯函数）：
   - `addSession / listSessions / volume / e1rm / weeklySets / pr`
   - 旧 `lifeflow-train-records` → sessions 迁移（按日期 + 时间邻近归组，幂等）
2. 记录页改为「开始训练 → 记录组 → 结束训练」：
   - 开始记 `start`，结束记 `end`，`durationMin` 只写一次；
   - `LightStore.record({mod:'运动', metric:'minutes', value:durationMin, meta:{sessionId}})`；
   - 删除「每个动作 +10 分钟」的假数据。
3. 迁移后体账户/灯仍能工作；历史假数据保留但不参与新统计（或按天去重）。

**验收**：一次 55 分钟训练，账本只多 55 分钟；体账户 = 55/30 封顶 100%。

### P1 · 让数据能指导训练（3–4 天）

1. **RPE/RIR**：每组一个 6–10 的 RPE 选择（默认上次值），RIR = 10 − RPE。
2. **组间休息计时器**：按动作类型默认 90/150/180 秒，自动开始。
3. **上次成绩提示**：动作卡片显示「上次 80kg×5@8」，一键复制。
4. **进步建议**（规则透明，不做黑箱）：
   - 所有组达到目标次数上限且 RPE ≤ 8 → 下次 +2.5kg（上肢）/ +5kg（下肢）；
   - 连续 2 次未达下限或 RPE ≥ 9.5 → 重量 −10%，或减一组；
   - 每 4–6 周或连续 3 次 RPE ≥ 9 → 建议 deload（容量 −40%，强度 −10%）。
5. **周报**：每肌群有效组数、频率、容量趋势、PR。

### P2 · 恢复与有氧（3–5 天）

1. **准备度**（1–5）：睡眠/酸痛/精神，≤2 时建议容量 −20%。
2. **有氧分区**：Zone2 / 间歇；记录时长、距离、平均心率；周目标 150 分钟中等强度。
3. **计划模板**：推/拉/腿、上下肢、全身 3 日；不再写死「练 3 休 1」。
4. **动作库**：肌群、器械、动作模式（蹲/髋/推/拉/核心），支持自定义。

## 四、科学规则（可写进产品文案）

| 原则 | 落地 |
|---|---|
| 渐进超负荷 | 达到次数上限且 RPE≤8 → 加 2.5–5kg |
| 容量 landmarks | 每肌群每周 8–10 组（MEV）、12–18（MAV）、20+（MRV，需恢复支持） |
| 频率 | 每肌群每周 2 次优先于一次练到酸 |
| 强度分布 | 增肌 6–15RM 为主；力量 3–6RM；保留 1–3 RIR |
| 恢复 | 同肌群间隔 ≥48h；睡眠 7–9h |
| Deload | 每 4–6 周或表现下降/RPE 持续升高时，容量减半 |
| 有氧 | 每周 150 分钟中等或 75 分钟高强度；80/20 极化 |

## 五、账户与灯的口径

现在体账户把「训练分钟」和睡眠/饮水/饮食平均，训练只占 1/7，且分钟是假的。

建议：

- **记录真实 session 时长**，`运动` 目标仍 30 分钟/天；
- 体账户保持平均，但训练卡片单独显示「本周 3/4 次 · 下肢 12 组」；
- 如果想让训练更有存在感，在灯页加「训练」小分，不改变体账户权重。

---

## 六、不要做（现阶段）

- 不做社交/排行榜/课程视频；
- 不做手表/HealthKit 同步（无后端、权限复杂）；
- 不做复杂周期化（没有 4 周数据前）；
- 不把三个页面推倒重写，先加共享 `training.js`，页面逐步接。

---

## 七、建议的落地顺序

1. **P0**：session 模型 + 真实时长 + 迁移（先把账算对）
2. **P1**：RPE + 休息计时 + 上次成绩 + 进步建议
3. **P2**：周报 + deload + 有氧分区 + 模板

每步都可独立上线；P0 完成后，后面的数据才有意义。
